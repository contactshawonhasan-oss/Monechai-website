# VPS deployment runbook (draft until live acceptance)

This app needs a running Next.js **Node** server and managed PostgreSQL (Supabase recommended); static HTML hosting will not process orders. Goal 10 started early: Docker builds locally, but production deployment is **not certified** while goals 05–09 and owner configuration remain open. Single instance only: multi-instance deployments need cache coordination and consistent Next server-function encryption keys/build IDs. See [Next self-hosting](https://nextjs.org/docs/app/guides/self-hosting).

## Owner prerequisites and configuration

- A Linux VPS with supported Docker (or Node 22 + npm), outbound TLS access to the database and Supabase; domain and TLS via an origin certificate/Let's Encrypt, optionally Cloudflare proxy. No database needs to run on the VPS.
- `DATABASE_URL` — **SECRET**, pooled PostgreSQL app connection from Supabase Dashboard → Connect. `DIRECT_URL` — **SECRET**, direct DB connection from Connect for migrations (may equal app URL for non-pooled local DB). `DATABASE_SSL=require` for Supabase; `disable` **only** on private/local PostgreSQL. Do not expose either URL in Docker build args, logs or `NEXT_PUBLIC_*`.
- `NEXT_PUBLIC_SITE_URL` — **PUBLIC**, verified canonical HTTPS origin, e.g. `https://shop.example.com`, **no path**. `NEXT_PUBLIC_SUPABASE_URL` — **PUBLIC** project URL; `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — **PUBLIC** publishable key (Supabase Dashboard → Project Settings → API / Connect). Pass these **before build** and also at runtime; they are inlined into client JS and image host config. Never use a service-role key here. Configure Supabase Auth site URL/redirect allowlist to the actual HTTPS domain and create/invite an owner Auth user per [admin bootstrap](admin-bootstrap.md).
- Create a public Supabase Storage bucket named `products` with restrictive upload/delete permissions and documented media backup before enabling product publishing. Goal 06 image management/policy validation is not complete; do not go live yet. No payment keys: only COD is implemented.
- Owner must configure real shipping zone rates and contact/business settings before accepting checkout. `scripts/configure-shipping.mjs` requires owner-approved `SHIPPING_INSIDE_DHAKA_MINOR`, `SHIPPING_OUTSIDE_DHAKA_MINOR` and optional `SHIPPING_FREE_ABOVE_MINOR` (integer poisha). Dry-run with `npm run shipping:configure` before `npm run shipping:configure -- --apply`; see [checkout goal](goals/goal_04_cart_checkout.md). Never use demo seed on production.
- Store runtime secrets in a root-readable env file outside the checkout, e.g. `/etc/monechai/runtime.env` (`chmod 600`), not in git or the Docker image; give only authorized operators access to Docker, which can inspect container environment. Public build args are visible in image history and should **never contain secrets**.

## Release procedure

1. Back up and confirm a restore point using [backup runbook](backup-recovery.md). Pin an immutable git revision and review changes to `src/db/migrations`. Take the shop offline for incompatible schema changes; use additive, backwards-compatible migrations for zero-downtime updates. Do not regenerate a migration against live data to resolve drift.
2. On a trusted deploy workstation/CI with **migration-only secrets**: `npm ci`, then `npm run db:migrate` with `DIRECT_URL` injected from the secret manager (not as a literal shell command). Verify migration success and review SQL **before** deploying app. Do not include production DB URLs in shell history or CI logs; use masked secrets/injected environment. To run demo data in disposable development only: `npm run db:seed` (refuses production).
3. Build: `docker build --build-arg NEXT_PUBLIC_SITE_URL=https://shop.example.com --build-arg NEXT_PUBLIC_SUPABASE_URL=https://PROJECT.supabase.co --build-arg NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=PUBLIC_KEY -t monechai:REVISION .`. Promote that exact image rather than rebuilding with different public settings. Do not pass `.env` to build. Alternatively `npm ci && npm run build`; standalone requires `.next/standalone`, `.next/static`, and `public/` copied to deployment directory; run `node server.js` with `HOSTNAME=127.0.0.1 PORT=3000` under an unprivileged service user. `npm start` runs `.next/standalone/server.js` in a source checkout but needs `.next/static` and `public/` alongside standalone for full asset serving.
4. On VPS, run one container: `docker run -d --name monechai --restart unless-stopped --env-file /etc/monechai/runtime.env -p 127.0.0.1:3000:3000 monechai:REVISION`. Set runtime public vars to the same values used at build. Keep Docker port loopback-only and restrict firewall; allow at least 30 seconds graceful stop time for in-flight requests when replacing container. Replace only after new instance and health checks pass; a canary should point to the same migrated schema.
5. Install TLS reverse proxy using [`ops/nginx-monechai.conf`](../ops/nginx-monechai.conf) as a template. Replace example hostname; test `nginx -t` and reload. The origin must be TLS-protected even when using Cloudflare. Cloudflare **Full (strict)** validates origin certificates ([official guide](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)); don't use Flexible. Forward the real visitor IP only from trusted Cloudflare ranges/proxy and block direct Node access before enabling `CHECKOUT_TRUST_PROXY_IP_HEADER=true`. Leave it unset otherwise. Do not cache `/admin`, `/api/*`, `/checkout`, `/order/*` or session-dependent HTML at Cloudflare or the proxy. Respect `Cache-Control` and avoid 'cache everything' rules.
6. `curl -i https://shop.example.com/api/health` must return HTTP 200 and `{"status":"ok","database":"ok"}`; 503 means DB unavailable (never count as healthy). Verify public shop, nonmember/admin redirects, authenticated catalog/order journeys, valid COD order with owner-approved fees, and checkout idempotency using test fixtures, then clean fixtures. Configure an external uptime check for `/api/health` and an error tracker with PII redaction. Do not log customer names, phone, address, order tokens, cookies, request bodies or database URLs.

Rollback: keep previous immutable image; roll back app **only if schema remains compatible**. Do not run an unreviewed down migration on live orders. For destructive data changes, take traffic offline and follow [recovery procedure](backup-recovery.md). Monitor HTTP 5xx, 503 health, checkout failure rates and disk space; rotate secrets after exposure. No actual VPS, DNS, Cloudflare or Supabase configuration was performed by this repository.

## Quick troubleshooting

- `/api/health` 503: verify runtime DB URL, network/TLS and migration status privately (avoid logging credentials); DB health requires a live connection.
- Admin login fails: check build-time and runtime Supabase public settings, Auth redirect allowlist, confirmed user and `admin_members` ([bootstrap](admin-bootstrap.md)).
- Missing CSS/images: ensure `.next/static` and `public` accompany standalone; verify public `products` Storage bucket and image-host build config.
- No checkout shipping quote: configure **owner-approved** rates; do not silently substitute sample prices.
