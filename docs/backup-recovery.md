# Backup and recovery (operator runbook)

**No backups are configured or verified in this repository.** Before taking real orders, the owner must choose and test an independent backup plan with a documented recovery point objective (RPO), recovery time objective (RTO), retention, encrypted off-site copies and a named operator. Database **and** Supabase Storage objects are needed for full recovery. Review current [Supabase backup documentation](https://supabase.com/docs/guides/platform/backups) and [backup/restore CLI guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) at each production rollout (checked 2026-10-08). The provider currently describes 7 days of daily backups on Pro, 14 on Team, up to 30 on Enterprise; Free should regularly export off-site with CLI `supabase db dump`. PITR is a separate option where eligible; confirm plan/project settings and retention in the actual Dashboard → Database → Backups, not from this document. A DB backup includes Storage **metadata only**, not object bytes; deleted image files are not restored by restoring the database.

## Before migration or release

1. Verify what is actually enabled in Dashboard → Database → Backups, the last successful backup timestamp, restore point and whether PITR is enabled. Check external dump schedule and integrity. Record a maintenance/recovery window.
2. Make an encrypted logical DB export to controlled off-site storage via the current official Supabase CLI `supabase db dump` flow (or provider daily backup). Use a least-privileged authorized backup account; keep the DB URL in a protected secret store, never a checked-in script, CLI history, Docker build, or support ticket. Prefer vendor-managed backups as the primary restore path for a Supabase-hosted project; check CLI version/options against vendor docs before a live dump/restore.
3. Export **Storage objects** from bucket `products` using an authorized, audited operator procedure (and preserve object keys). Keep DB snapshot and Storage snapshot time-aligned; a DB-only restore can point to missing images. Retain encryption keys separately from the backups, verify checksums and restricted access, and schedule periodic restore drills in an isolated project.
4. Review migration SQL, especially irreversible DDL and enum/status changes. Save a compatible previous image. Do not use demo seeds or destructive `db:generate`/`db:push` as a live rollback.

## Recovery drill / incident

1. Stop new writes/checkouts and restrict the origin. Capture incident time, latest known-good backup and expected data-loss window; notify owner of potential lost/duplicate orders. Do not assume rollback of a Docker image rolls back PostgreSQL.
2. Restore to a **separate isolated Supabase project/database** first, following provider instructions. Never restore blindly over live orders. Recreate any custom role passwords/grants as instructed by provider; verify Auth users, `admin_members`, catalog, stock, settings, orders, order items and migration journal. Restore/check Storage object bytes and bucket policies. A restored `admin_members` row is not proof of an active Auth user.
3. Run health/read-only checks and one controlled checkout on the isolated environment with non-customer test data. Reconcile orders created since backup from an authorized source before cutover; inventory, COD and idempotency records must not be guessed. Avoid replaying customer payments (only COD is supported). Obtain owner signoff before DNS/app cutover.
4. Rotate compromised credentials, restore traffic gradually and monitor health/5xx/orders; record actual RPO/RTO and prevent recurrence. A restored historical snapshot can overwrite more recent orders if reused as live DB; recover with an explicit reconciliation plan.

Observability: use `/api/health` for DB readiness (200 or 503), alert on failures, and redact customer PII, public order tokens and secrets from logs/error tracking. This document is guidance, **not** evidence that an export or restore was performed.
